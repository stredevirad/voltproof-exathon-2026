# Contributing to VoltProof

Thank you for helping. VoltProof turns ESMI minute-wise voltage records from Prayas (Energy Group) into
traceable evidence of power cuts and poor supply. The analysis runs inside Exasol Personal. Setup:
[docs/SETUP_WINDOWS.md](docs/SETUP_WINDOWS.md).

## Ground rules

- **The analysis lives in SQL** (`sql/`, run inside Exasol). Python only orchestrates, loads, presents,
  and hosts the independent test oracle (`tests/oracle/`). Do not move a calculation into Python.
- **Missing data is never an outage.** A minute without a reading is "no reading". An event next to a
  gap gets a minimum and a maximum duration, and the headline uses the minimum.
- **Every threshold or parameter** goes in `config/method.yaml` with its primary source (URL and
  retrieval date). Never change a parameter just to match a published figure.
- **Never commit raw data.** `data/` is gitignored. Users download the ESMI files themselves from Harvard
  Dataverse. The SYNTHETIC demo set is generated by `pipeline/synthetic.py` and is never mixed with
  real data (DECISIONS D-033).

## Running the tests

| Command | Needs | What it runs |
|---|---|---|
| `scripts\test.ps1 -Suite unit` | nothing | unit tests (CI runs these) |
| `.venv\Scripts\ruff.exe check .` | nothing | lint (CI runs this; the rule set is in `pyproject.toml`) |
| `scripts\test.ps1` | a running database and a built schema | unit, integration, differential, end-to-end |
| `scripts\test.ps1 -Suite e2e -Part test_demo_flow.py` | the same | one file of one suite |

- Run the database suites through `scripts\test.ps1`, not plain `pytest`. The script picks the schema:
  `VOLTPROOF_SCHEMA` if set, else `VOLTPROOF` if built, else `VOLTPROOF_DEMO`. Plain `pytest` assumes
  `VOLTPROOF`.
- The fastest way to get a schema is `scripts\load.ps1 -Set demo`, which needs no download.
- CI (GitHub Actions) runs only the lint and the unit tests. The other suites need Exasol Personal
  (Podman/WSL 2, about 9 GB of RAM for the database), which hosted runners do not provide.
  `docs/TEST_REPORT.md` records the latest full local run.

## Wording: the claims vocabulary

VoltProof shows what the monitors measured. It does not establish causes or legal outcomes.

- Coincident interruptions are a **"potential shared supply event"**. Never name a piece of equipment as
  the cause, and never call a shared cause established.
- A record **"may warrant review through"** a named grievance route. Never say that it establishes a
  right, a payment or a conclusion.
- Keep measured and inferred apart in every string, and label anything illustrative or simulated as
  **Illustrative**.
- Wherever the data appears, attribute it to "Prayas (Energy Group), Electricity Supply Monitoring
  Initiative (ESMI)".

The banned phrases are listed once, in `tests/support/claims.py`; this file describes them in words.
Two tests enforce the list:
- `tests/unit/test_published_text.py` scans every tracked text file;
- the integration and end-to-end tests scan the app pages and the generated reports.

If a test flags your text, reword it. Do not add an exemption.

## Adding a test fixture

Fixtures are small hand-written ESMI files with expected results derived by hand. Details:
[tests/fixtures/README.md](tests/fixtures/README.md).

1. Copy an existing `tests/fixtures/Fxx_*.yaml` to the next free number with a descriptive name.
2. Fill in:
   - `rules`: the METHODOLOGY rule ids it exercises;
   - `params`: any overrides of `config/method.yaml`;
   - `locations`;
   - `hours`: wide rows in the ESMI layout, in run notation such as `230*10 0*5 _*45`, where `_` is a
     blank cell.
3. Write `expected` **by hand from the rules**, each value with a one-line `why`. Never paste output from
   our own code.
4. Render the CSVs: `.venv\Scripts\python.exe -m tests.fixtures.render`. Commit the YAML and
   `tests/fixtures/rendered/<fixture>/`.
5. Run `scripts\test.ps1 -Suite integration`. The fixture must meet its hand-written expectations, and
   the SQL output must equal the independent oracle (`tests/oracle/`).

## Commits and pull requests

- Keep commits small, with a message that says what changed and why.
- Before pushing, run the unit tests and ruff, and make sure no `.env`, `secrets.json` or `data/` file is
  staged.
- A pull request that changes the SQL or the method should also update `docs/METHODOLOGY.md` and, for a
  decision, add an entry to `docs/DECISIONS.md`.
